<task id="2" type="auto">
<description>Rewrite legacy D-Bus CreateTunnel to forward to AdapterClient</description>
<read_first>
- multi-tunnel-namespace/src/libvpnmanager/dbus/service.py (ManagerService.CreateTunnel method)
- multi-tunnel-namespace/src/libvpnmanager/client.py (AdapterClient)
</read_first>
<action>
1. Replace the body of `CreateTunnel` with a forwarding implementation:
   - Extract `config` and `username` from D-Bus parameters.
   - Determine adapter_type from config (e.g., `config['adapter']` or default).
   - Build credentials dict with `username` and `password`.
   - Call `self.manager.start_adapter(adapter_type, credentials, session_token=...)`. The `session_token` should be taken from the D-Bus call parameters if present (to satisfy TOTP mode requirement). This ensures adapter is running.
   - Receive `adapter_info` with `endpoint`.
   - Create `AdapterClient` with that endpoint and pass `totp_code` from the D-Bus call parameters (if any) to the client.
   - Build `ConnectionConfig` from the config dict (use existing model conversion).
   - Call `await client.create_tunnel(tunnel_name, conn_config)`.
   - Optionally call `await client.connect_tunnel(tunnel_name)` if the legacy method was supposed to connect automatically.
   - Return the tunnel result as D-Bus variants (same format as before).
2. Preserve error handling: if `start_adapter` fails, raise appropriate D-Bus errors (`AdapterNotFoundError`, `AuthenticationError`).
3. Ensure the method still registers the tunnel with any manager-level state if needed; but the tunnel is created by the adapter. The legacy caller expects a result; returning adapter's tunnel info is sufficient.
</action>
<acceptance_criteria>
- `CreateTunnel` calls `self.manager.start_adapter` first.
- Then uses `AdapterClient` to call `create_tunnel` (and `connect_tunnel` if appropriate).
- Does NOT call `self.manager.create_tunnel` directly.
- Returns tunnel dict in the same shape as before (D-Bus variants).
- Handles errors from start_adapter appropriately.
</acceptance_criteria>
</task>

<description>Forward other legacy tunnel methods (DestroyTunnel, ConnectTunnel, DisconnectTunnel, ListTunnels, GetTunnelStatus)</description>
<read_first>
- multi-tunnel-namespace/src/libvpnmanager/dbus/service.py (remaining methods)
- multi-tunnel-namespace/src/daemon/daemon.py (tunnel_to_adapter mapping)
</read_first>
<action>
For each method:

**DestroyTunnel(tunnel_name):**
- Look up adapter using `self.daemon.tunnel_to_adapter[tunnel_name]` to get endpoint.
- Create `AdapterClient(endpoint, totp_code=...)` (totp from params if present).
- Call `await client.destroy_tunnel(tunnel_name)`.
- Remove mapping entry (or rely on adapter's ReleaseTunnel to remove; but to be safe, also remove from mapping).
- Return success/failure.

**ConnectTunnel(tunnel_name, totp_code?):** Similarly forward to `client.connect_tunnel(tunnel_name)`.

**DisconnectTunnel(tunnel_name, totp_code?):** Forward to `client.disconnect_tunnel(tunnel_name)`.

**GetTunnelStatus(tunnel_name):** Forward to `client.get_status(tunnel_name)` and return result.

**ListTunnels():** Option 1: iterate over all adapters and aggregate their `list_tunnels()` results. Option 2: return combined view from manager's tunnel registry? Simpler: query each adapter via `AdapterClient.adapter_list_tunnels()` if such method exists, or we add a method to adapter to list its tunnels. According to Phase 2, adapter has `list_tunnels` method. So:
   - Get list of all adapters from `self.manager.list_adapters()`.
   - For each adapter endpoint, create `AdapterClient` and call `list_tunnels()`, collect results.
   - Return combined list.
   (Note: This may be heavy but acceptable.)

Implement each method accordingly. Ensure error handling consistent: if tunnel not found, raise `TunnelNotFoundError`; if adapter not found, raise `AdapterNotFoundError`.
</action>
<acceptance_criteria>
- `DestroyTunnel`, `ConnectTunnel`, `DisconnectTunnel`, `GetTunnelStatus` all use `AdapterClient` to forward to the owning adapter.
- `ListTunnels` aggregates results from all adapters.
- No direct calls to `self.manager.*` for tunnel operations (except possibly to maintain state, but forwarding is primary).
- Each respects TOTP by passing `totp_code` if provided.
</acceptance_criteria>
