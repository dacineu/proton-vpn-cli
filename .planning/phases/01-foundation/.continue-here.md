<decisions_made>

- **CLI-level 2FA model**: MTM is sole keeper of TOTP secret (encrypted in keyring). CLI never stores secrets; prompts user each time (or uses cached recent TOTP). Adapter receives TOTP secret at spawn via stdin, validates per-request TOTP codes. Every request (CLI→MTM, CLI→Adapter, Adapter→MTM) includes fresh TOTP code.
- **Token validation simplification**: Adapter validates only `session_token` (passed by MTM at spawn) rather than re-verifying TOTP. This trusts MTM's spawn decision; adapter only needs to bind CLI to this specific adapter session. Phase 1 uses dummy tokens (random strings); Phase 4 adds real TOTP verification at MTM before issuing token.
- **Socket paths**: `/run/mtm/adapters/{username}_{adapter_type}.sock` for CLI, `/run/mtm/control/{username}_{adapter_type}.sock` for adapter→MTM control. Directories created by MTM at startup with 0755, socket files 0600.
- **Control protocol**: NDJSON (newline-delimited JSON), request-reply pattern, error format `{"status": "error", "error": "...", "code": "UPPER_UNDERSCORE", "details": {}}`. Authentication via SO_PEERCRED on control socket to verify UID matches claimed username.
- **Credential security**: Adapter receives VPN credentials via stdin (not env); immediately zeroizes buffer after login. Only VPN session tokens remain in memory.
- **Dummy adapter**: Realistic simulation: varying device names (dummy0, dummy1...), 500ms-1s artificial delay, implements full API (CreateTunnel, DestroyTunnel, ListTunnels, GetStatus), tracks tunnels in self.tunnels dict, sends AllocateTunnel to MTM even if namespace mocked.
- **Adapter lifecycle**: StartAdapter checks adapter_pool[(type, vpn_username)]; if alive returns existing endpoint. Spawns new only when none alive. Generates session_id (UUID). Waits only for CLI socket bind (10s timeout), not VPN login. StopAdapter sends Shutdown control message.
- **Concurrency**: Adapter uses asyncio.Lock to protect self.tunnels modifications; multiple CLI connections can be served concurrently (serialized on critical sections).
- **Token flow in Phase 1**: Daemon generates random `session_token`, passes to adapter via env `SESSION_TOKEN` or Register response. Adapter stores `expected_session_token`, validates on every CLI request. No actual TOTP verification yet.

</decisions_made>
