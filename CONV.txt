  Current Architecture Limitations

  The current Proton VPN CLI is designed for single-connection, system-wide routing:

  1. One tunnel at a time - The daemon creates a single TUN device (proton0)
  2. System-wide routing - Default route is modified to go through the VPN
  3. Single user context - All connections are per-user but system-wide
  4. Global state - One active connection managed by the daemon

  Proposed Architecture: Multi-Tunnel + Network Namespaces

  Option 1: Network Namespaces (Recommended)

  Each VPN connection runs in its own network namespace, providing complete isolation:

  +-------------------------------------------------------------+
  |                     Host System (netns: default)           |
  |  +-------------+  +-------------+  +-------------+       |
  |  |   Terminal  |  |   Browser   |  |   Other     |       |
  |  |   (app1)    |  |   (app2)    |  |   apps      |       |
  |  +------+------+  +------+------+  +------+------+       |
  |         |                 |                 |              |
  |         +-----------------+-----------------+              |
  |                           |                               |
  |                     +------?------+                      |
  |                     |  Routing    |                      |
  |                     |  Table      |                      |
  |                     +-------------+                      |
  +-------------------------------------------------------------+
           |
           +- (namespace: vpn1) ---> proton0 ---> VPN server 1
           |
           +- (namespace: vpn2) ---> proton1 ---> VPN server 2

  How it works:
  - Each tunnel runs in a separate network namespace (e.g., vpn-proton-1, vpn-proton-2)
  - The protonvpn connect --tunnel-name mytunnel creates a new namespace
  - Applications launched from that shell are moved to the namespace
  - Each namespace has its own routing table and TUN device

  Implementation:
  # Create and connect to a named tunnel
  protonvpn connect --tunnel-name work --country US

  protonvpn connect --tunnel-name personal --country JP

  protonvpn tunnel switch work
  firefox  # goes through work tunnel

  # Switch to personal tunnel in same shell
  protonvpn tunnel switch personal
  curl https://ifconfig.me  # goes through personal tunnel

  # Or launch app directly in tunnel
  protonvpn tunnel exec personal -- telegram-desktop

  CLI commands needed:

  +-------------------------------------------------------------+
  |                     Host System                             |
  |                                                              |
  |  +-------------+         +-------------+                   |
  |  |   Terminal1 |         |   Terminal2 |                   |
  |  |   (mark:1)  |         |   (mark:2)  |                   |
  |  +------+------+         +------+------+                   |
  |         |                       |                           |
  |         +-------------+---------+                           |
  |                       ?                                      |
  |              +----------------+                             |
  |              |  iptables MARK |                             |
  |              +----------------+                             |
  |                       |                                       |
  |              +--------?--------+                             |
  |              |  Routing Tables |                             |
  |              |  table1 (vpn1)  |                             |
  |              |  table2 (vpn2)  |                             |
  |              +--------+--------+                             |
  |                       |                                       |
  |              +--------?--------+                             |
  |              |  Rule lookup    |                             |
  |              +------------------+                             |
  +-------------------------------------------------------------+

  How it works:
  - Each tunnel gets its own routing table (e.g., table 1001, table 1002)
  - iptables marks packets from processes in a specific cgroup or with specific fwmark
  - Policy routing rules select routing table based on fwmark
  - All tunnels can be active simultaneously; routing decides which tunnel each packet uses

  Implementation:
  # Create tunnel with specific routing table
  protonvpn connect --table 1001 --country US

  # Mark current shell's processes
  protonvpn tunnel mark 1001
  firefox  # gets fwmark 1001, uses VPN1

  # Different shell, different mark
  protonvpn tunnel mark 1002
  telegram  # gets fwmark 1002, uses VPN2

  CLI commands:
  - protonvpn tunnel mark <table-id> - Mark current session
  - Use cgroup or iptables to apply marks to process tree

  Advantages:
  - No network namespace overhead
  - Processes can be moved between tunnels easily
  - All tunnels active at once

  Disadvantages:
  - More complex routing rules
  - Potential conflicts with existing rules
  - Requires iptables/nftables manipulation

  Option 3: SOCKS5 Proxy per Tunnel

  Simpler but requires application support:

  protonvpn connect --proxy-port 1080 --country US  # Creates SOCKS5 proxy

  Advantages:
  - Easy to implement (no kernel changes)
  - Works across network namespaces easily
  - Application-level control

  Disadvantages:
  - Only works for proxy-aware apps
  - DNS may leak if not handled
  - UDP support limited (SOCKS5 UDP ASSOCIATE)

  Challenges & Considerations

  1. Complexity: This is a major architectural change requiring daemon modifications
  2. Kernel limits: Number of TUN devices, routing tables, namespaces
  3. Resource usage: Each tunnel consumes memory, file descriptors
  4. DNS: Each namespace needs its own DNS resolver (e.g., systemd-resolved per-ns)

  7. Graceful degradation: What if tunnel creation fails?
  8. Persistence: Should tunnels survive reboot? Probably not.
  9. User experience: Commands need to be intuitive
  10. Documentation: Substantial docs needed

  Multi-Tunnel Architecture Design: Application-Independent Approach

  Vision

  Create a reusable library and daemon architecture that enables:
  - Multiple concurrent VPN tunnels (each with its own TUN/TAP device)
  - Per-application routing (run specific apps through specific tunnels)
  - Vendor-neutral design (support Proton VPN, Psiphon, WireGuard directly, OpenVPN, etc.)
  - Extensible adapter pattern for new VPN types

  ---
  Core Design Principles

  1. Separation of Concerns:
    - Tunnel Manager: Lifecycle (create, destroy, list tunnels)
    - Routing Engine: How traffic is routed (namespaces, policy routing, proxies)
    - VPN Adapters: Backend-specific connection logic (Proton, Psiphon, etc.)
    - CLI/UI: User-facing commands
  2. Adapter Pattern:
  class VPNAdapter(Protocol):
      async def connect(self, config: ConnectionConfig) -> Tunnel:
          """Establish VPN connection and return tunnel object"""
      async def disconnect(self, tunnel: Tunnel):
          """Disconnect specific tunnel"""
      async def get_status(self, tunnel: Tunnel) -> TunnelStatus:
          """Get connection status"""
      def get_tunnel_devices(self) -> List[Tunnel]:
          """List active tunnels this adapter manages"""
  3. Tunnel Abstraction:
  @dataclass
  class Tunnel:
      name: str
      adapter_type: str  # "proton", "psiphon", "wireguard", etc.
      device_name: str   # "proton0", "tun0", etc.
      routing_table: Optional[int] = None  # For policy routing
      network_namespace: Optional[str] = None  # For namespace isolation
      endpoint: str  # Server/exit node
      connected_at: datetime
      metadata: Dict[str, Any]
  4. Routing Strategies (pluggable):
    - Network Namespace: Each tunnel in isolated ns
    - Policy Routing: Routing tables + fwmark
    - Proxy: SOCKS5/HTTP per tunnel
    - Interface-based: Bind app to specific interface (least flexible)
