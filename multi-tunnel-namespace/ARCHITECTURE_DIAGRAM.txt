KEY FLOW: Creating a tunnel named "work"
────────────────────────────────────────────────────────────────────────────────

1. User: $ protonvpn tunnel create work --country US
   │
   ├─> CLI: VPNManagerClient.CreateTunnel(config)
   │      (D-Bus call to daemon)
   │
2. Daemon: TunnelManager.create_tunnel("work", config)
   │
   ├─> Gets adapter (ProtonVPNAdapter)
   │
3. Adapter: connector.connect("work", server_us, "wireguard")
   │           (MultiTunnelVPNConnector)
   │
   ├─> Allocates TUN name: "proton0"
   │
   ├─> LocalAgent.connect(server, "wireguard", tun_device_name="proton0")
   │           └─> Creates /dev/net/tun device "proton0"
   │               Establishes encrypted tunnel to US server
   │               Returns VPNConnection
   │
4. Adapter: Returns Tunnel object with device="proton0"
   │
5. Manager: routing.create_tunnel_context("work")
   │           └─> Creates namespace "vpn_work"
   │
6. Manager: routing.move_device_to_namespace("proton0", "vpn_work")
   │           └─> ip link set proton0 netns vpn_work
   │
7. Manager: routing.configure_namespace_network(...)
             └─> Inside vpn_work namespace:
                 • ip link set proton0 up
                 • ip addr add 10.8.0.2/32 dev proton0
                 • ip route add default via 10.8.0.1
                 • cp resolv.conf with Proton DNS
   │
8. Daemon: Returns tunnel info to CLI
   │
9. CLI: Prints success message
   │
10. User: $ protonvpn tunnel switch work
    │
    └─> CLI: Uses nsenter to launch shell in vpn_work namespace
            Now in that namespace → all apps use work tunnel

TECHNICAL DECISIONS HIGHLIGHTED:
────────────────────────────────────────────────────────────────────────────────

1. Each tunnel gets unique TUN device ("proton0", "proton1", ...) from daemon
2. Each tunnel gets its own network namespace ("vpn_work", "vpn_personal")
3. TUN device moved to namespace immediately after creation
4. Routing configured INSIDE namespace (separate from host)
5. User enters namespace via nsenter for per-app routing
6. All namespaces can be active simultaneously (multi-tunnel achieved!)
7. Complete isolation: no DNS leaks, separate routing tables, separate iptables

COMPARISON: Single-Tunnel vs Multi-Tunnel (Our Design)
═══════════════════════════════════════════════════════════════════════════════

Single-Tunnel (Current):
  ┌────────────────────────┐
  │ protonvpn CLI          │
  └─────────────┬──────────┘
                │ connect US or JP
                ▼
  ┌────────────────────────┐
  │ Daemon                 │
  │ Creates → proton0      │
  │ Configures → default   │  Only ONE tunnel active
  │ route via proton0      │  All traffic goes through it
  └────────────────────────┘

Multi-Tunnel (Our Design):
  ┌────────────────────────┐
  │ protonvpn CLI          │
  │ tunnel create work     ├──┐
  │ tunnel create personal ├──┼──> Multiple concurrent
  └─────────────┬──────────┘  │    connections
                │              │
                ▼              ▼
  ┌────────────────────────┐  ┌────────────────────────┐
  │ Daemon: TunnelManager  │  │ Create: vpn_work ns    │
  │  ├─ work → proton0     │  │ Move: proton0→vpn_work│
  │  ├─ personal → proton1│  │ Config: inside ns     │
  │  └─ ... → protonN      │  └───────────────────────┘
  │                       │
  │ MultiTunnelVPNConnector│  ┌────────────────────────┐
  │   (tracks N tunnels)  │  │ Create: vpn_personal ns│
  │                       │  │ Move: proton1→ns      │
  └───────────────────────┘  │ Config: inside ns     │
                            └───────────────────────┘
  Users use: tunnel switch work
            tunnel switch personal
            (namespace isolation)
